01 · begin

Start with one normal Vite entry point.

New to the framework? Choose Minimal, JavaScript, and ordinary CSS first. Keep the generated bootstrap and layout, then follow the two-file homepage walkthrough. The full site you are reading lives in examples/velodom-blog; the generated Blog starter is a smaller editable application.

The recommended application bootstrap discovers pages, components, layouts, file API routes, and middleware conventions. Advanced apps can still use createViteApp() or createApp() explicitly.

src/main.jsJavaScript or TypeScript
import { mountVeloDom } from "velodom/vite";

await mountVeloDom();
Mental model: Folder = feature. HTML = template. A nearby script owns behavior, a config owns route policy and SEO, and the compiler assembles the resource map.

02 · authoring

Pages stay visible and close to their policy.

Folder mode is the default for a growing feature. The optional .vd format co-locates template, script, style, and config without replacing folders. Both use the same compiler and runtime contracts.

folder moderoute feature
src/pages/about/
├── index.html   # template
├── script.js    # state + lifecycle
├── style.css    # scoped presentation
├── data.js      # optional page data
└── config.js    # path, layout, guards, SEO

Shallow state is the shortest path to interaction.

Export plain defaults for simple behavior. Move multi-step work, async logic, event subscriptions, and cleanup into init().

src/pages/counter/state + event
<!-- index.html -->
<h1>{{ title }}</h1>
<button vd-on:click="count++">Count: {{ count }}</button>

// script.js
export const state = {
  title: "Hello VeloDom",
  count: 0
};

03 · templates

Directives add behavior without replacing HTML.

Preferred vd-* syntax is compiled and source-checked. Text interpolation is ideal for inline text; use vd-text when an element owns the whole value. Legacy data-vd-* input remains compatible for older templates.

conditions and loopssafe expressions
<p vd-if="Boolean(user)">Welcome {{ user.name }}</p>
<p vd-else>Please sign in.</p>

<ul>
  <li vd-for="post in posts" vd-key="post.id">
    {{ post.title }}
  </li>
</ul>
binding and form modeldeclarative UI
<input vd-model="draft.title" aria-label="Title">
<a vd-bind:href="post.url" vd-nav>Read post</a>
<div vd-class="{ active: isActive }"></div>
<div vd-style="{ '--BrandColor': accent, color: 'var(--BrandColor)' }"></div>
<button vd-attr="{ 'aria-pressed': isActive }">Toggle</button>

ARIA booleans become "true" or "false"; use null to remove an attribute. CSS variables retain their case. Try the accessible binding example.

Expression boundary: VeloDom parses expressions into an AST instead of using eval or new Function. Keep complex business logic in the page or component script.

05 · navigation

Folder paths become predictable client routes.

Nested folders map to nested routes and bracket folders map to params. VeloDom also supports route config overrides, guards, query values, route metadata, focus management, scroll restoration, hashes, and opt-in link prefetch.

routing by conventionfolders first
src/pages/
├── home/index.html            → /
├── blog/index.html            → /blog
└── blog/posts/[id]/index.html → /blog/posts/:id

<a href="/blog/posts/html-first" vd-nav>Read article</a>
<a href="/features#requests" vd-nav>Jump to requests</a>
src/pages/account/config.jspage guard
export default {
  meta: { requiresLogin: true },
  async beforeEnter({ to, from }) {
    const signedIn = await readSession();
    return signedIn ? true : "/login";
  }
};

// true / undefined → continue
// false            → block
// "/login"         → app-relative redirect
Guard order: global router.beforeEach functions run before the matched page's beforeEnter. They improve navigation UX; private data still requires server authorization.
Same-page hashes: the router updates history, scrolls and focuses without remounting, then emits hashchange for route-aware UI.

06 · data and forms

Keep common request UX declarative; keep business rules in src/api.

File route discovery and explicit registries both produce named request handlers. The browser can bind a request to a result destination and derive loading/error state. Middleware, auth providers, retry, cache, debounce, throttle, hooks, and validation remain opt-in.

07 · application API

Keep handlers and business rules in visible application files.

VeloDom discovers a nested default export in src/api as a named route. Root API modules remain ordinary helpers, while an explicit routes.js registry is the escape hatch for policies such as middleware, roles, and custom names.

src/api/posts/get-one.jssimple file route
import { requestJson } from "velodom";

export default function getOne({ id }, { signal } = {}) {
  return requestJson(`/api/posts/${id}`, { signal });
}

// The file path becomes: posts.get-one
src/api/routes.jsexplicit policy
import { createPost } from "./posts.js";

export default {
  "posts.create": {
    handler: createPost,
    middleware: ["trimStrings"],
    auth: true,
    roles: ["editor", "admin"]
  }
};
Ownership: src/api is browser code. Keep database credentials, payment secrets, permission decisions, and authoritative business totals on a separately deployed backend. This folder organizes the calls to that backend.

08 · authentication

Authentication is an optional provider, never a substitute for backend authorization.

Register one or more providers at bootstrap, then declare route policy where it is needed. A server-session provider is the recommended production boundary; the localStorage provider is intentionally for demos and prototypes only.

src/main.jsserver session provider
import { createServerSessionAuthProvider } from "velodom";
import { mountVeloDom } from "velodom/vite";

await mountVeloDom({
  auth: {
    defaultProvider: "server",
    providers: {
      server: createServerSessionAuthProvider({
        sessionUrl: "/api/auth/session",
        credentials: "include"
      })
    }
  }
});
src/api/routes.jsroute policy
export default {
  "profile.read": {
    handler: readProfile,
    auth: true,
    authRedirect: "/login"
  },
  "posts.update": {
    handler: updatePost,
    auth: "server",
    roles: ["editor", "admin"]
  }
};
Security boundary: the provider improves client UX and request coordination. The server must still verify the session, role, CSRF policy, and resource ownership.

The repository's examples/velodom-store runs a separate local HTTP fixture for sessions, catalog quotations, administration, and mock order status. It demonstrates tenant/owner denial, session expiry, CSRF checks, authoritative currency/price/stock/tax, and duplicate-write protection. Run npm run dev:store from the source checkout and open /sign-in. Mock orders never charge money. Production credentials and provider event verification belong to your backend.

09 · cache and resilience

Cache public data deliberately; retry only failures that are safe to repeat.

Page data may use a small memory cache for public, repeat-visited routes. Request caching and retries are explicit helpers. Mutations bypass the request cache; the application must keep private session and no-store endpoints outside it.

src/pages/catalog/data.jspage data cache
export async function load() {
  const response = await fetch("/api/catalog");
  return { products: await response.json() };
}

// Public data only — memory is cleared on full refresh.
export const cache = {
  maxAgeMs: 30_000,
  staleWhileRevalidateMs: 120_000
};
src/api/posts.jsGET cache + retry
import { createRequestCache, withRequestRetry } from "velodom";

const cache = createRequestCache({
  ttlMs: 30_000, maxEntries: 40, scope: "public-posts"
});

export const getOne = withRequestRetry(
  ({ id }, context) => cache.requestJson(`/api/posts/${id}`, {
    signal: context.signal
  }),
  { retries: 2, delayMs: 250 }
);

The optional request cache coalesces concurrent GET reads with independent cancellation, uses bounded LRU retention (100 entries by default), and fences older cache writes after clear(). Clear only after a confirmed successful mutation, then explicitly reload the UI. A failed write preserves the last good read.

Both retry forms use abortable waiting and never repeat AbortError or a cancelled request. Middleware stops before the next operation after cancellation. Forward context.signal to I/O; custom work that ignores it cannot be forcibly stopped. A binding disposed/replaced during an async success callback no longer sends late completion notifications. Aborting does not undo state already applied or a write accepted by the backend: use status and idempotency to recover.

Privacy and freshness: headers and credentials affect request identity, but HttpOnly cookie changes and HTTP cache headers are not inferred. Session/no-store endpoints stay uncached. For explicitly permitted private read caching, an app-owned scope must include tenant/user/session identity and be cleared on auth changes. Page-data caching is separate and public-only here. Legacy ttlMs: 0 means until clear/eviction; prefer a finite TTL. Never blindly retry checkout/create actions.

10 · RTL and direction

Direction is opt-in, while logical CSS keeps layouts naturally multilingual.

The optional direction plugin manages the document’s lang and dir attributes. It is separate from translation dictionaries, so an application can use its preferred localization source without carrying a mandatory i18n runtime.

src/main.jsdirection plugin
import { createDirectionPlugin } from "velodom";
import { mountVeloDom } from "velodom/vite";

await mountVeloDom({
  plugins: [
    createDirectionPlugin({
      defaultLocale: "en",
      locales: {
        en: { lang: "en", direction: "ltr" },
        ar: { lang: "ar", direction: "rtl" }
      }
    })
  ]
});
logical CSS + explicit iconRTL safe
.card {
  margin-inline-start: 1rem;
  padding-inline-end: 1rem;
  border-inline-start: 4px solid currentColor;
  text-align: start;
}

<svg vd-rtl-flip aria-hidden="true"></svg>
<p vd-text="$direction.direction"></p>
No blind mirroring: VeloDom never flips every icon automatically. Mark only directional icons with vd-rtl-flip; logos, media controls, and clocks often should remain unchanged. With the plugin installed, both page and component hooks receive the same optional ctx.direction controller.

11 · assets and lazy loading

Prefer browser-native lazy loading and build-time image information.

There is no heavyweight vd-lazy directive. Images use standard HTML loading and decoding hints, while responsive variants are explicit application assets. The compiler also emits a feature manifest so unused directive runtime modules are not activated for a page that does not need them.

13 · optional PWA

Choose offline behavior explicitly at build time.

The normal VeloDom runtime never installs a service worker. Projects that need installability can add a static manifest, application-owned offline page, and bounded cache policy through the separate velodom/pwa entry point.

terminaloptional setup
vd add pwa

# Or while creating a project:
npm create velodom@latest -- --pwa
src/pwa.jsbounded cache policy
export const pwaServiceWorker = {
  offlineFallback: "/offline.html",
  version: "v1",
  strategies: definePwaCacheStrategies([
    { cacheName: "pages", match: "navigation", strategy: "network-only" },
    { cacheName: "assets", match: "same-origin-assets",
      strategy: "stale-while-revalidate" }
  ])
};
Opt-in means opt-in: a manifest-only configuration emits no registration module. Authentication and API caching remain application policy, never a hidden framework default.

15 · optional visual inspection

VeloDom Lab explains a running app without becoming part of it.

Lab is an experimental, read-only Vite development layer. It displays the current route, nested page/component ownership, safe state snapshots and recent diffs, a payload-free request waterfall, correlated route transitions, directive/source locations, and copyable local diagnostic commands. 16 · reliability

Data, recovery, and browser safety stay explicit.

A page data module owns initial public data before a page initializes. The compiler reports common accessibility and security mistakes before delivery, while an application error boundary decides how a recoverable failure should look. None of these features creates a hidden server or a second rendering model.

src/pages/catalog/data.jsinitial public data
export async function load({ params, query, mode }) {
  const response = await fetch(`/api/catalog?tag=${query.tag || "all"}`);

  return {
    products: await response.json(),
    source: mode
  };
}

// Optional: public data only. This cache is memory-only.
export const cache = {
  maxAgeMs: 30_000,
  staleWhileRevalidateMs: 120_000
};
src/main.jsrecoverable boundary
await mountVeloDom({
  errorBoundary({ title, message, diagnostic, retry }) {
    console.error(diagnostic.code, diagnostic.ownership);

    const fallback = document.createElement("section");
    fallback.setAttribute("role", "alert");
    fallback.textContent = `${title}: ${message}`;

    const button = document.createElement("button");
    button.textContent = "Try again";
    button.addEventListener("click", () => retry());
    fallback.append(button);
    return fallback;
  }
});

Runtime failures carry a stable diagnostic ID, a compiler/router/ request/component/runtime group, a bounded normalized source stack, and an ownership trail. The optional development overlay observes the same reports; it never chooses the fallback or performs the retry.

17 · architecture

A small runtime is an architectural decision.

VeloDom Core receives resources from adapters. It does not discover your disk, own your business data, or import a framework-specific server. This boundary keeps an application free to use JavaScript or TypeScript while framework complexity stays inside a documented TypeScript package.

public importsstable boundaries
import {
  createApp, definePlugin, inspectPluginConformance
} from "velodom";
import { mountVeloDom } from "velodom/vite";
import { compileTemplate } from "velodom/compiler";
import {
  compileTestFixture,
  inspectAccessibilitySmoke,
  mountTestPage,
  resolveTestRoute
} from "velodom/testing";

const integration = definePlugin({
  manifest: {
    name: "example-tools",
    version: "1.0.0",
    velodom: "^1.0.0",
    capabilities: ["browser"]
  },
  setup() {}
});

inspectPluginConformance(integration, { target: "browser" });

// Do not import velodom/lib/* or packages/velodom/src/*
// Those are framework internals, not application APIs.

Grow by feature ownership, not another module system.

Keep discovered pages, components, layouts and API routes in their usual folders. Move reusable business behavior into explicitly imported application modules. The store reference separates catalog, cart, account UX and admin behavior; these folder names do not register framework services.

Deployment boundary: shared helpers must not import page scripts or server credentials. VITE_* values are public. A static build does not deploy a backend, and Vite asset base does not automatically prefix routes, links or API paths. The repository handbook checks the matching JavaScript/TypeScript lesson and both consumers against an installed local package.
Explicit non-goals: VeloDom does not require JSX/TSX, a virtual DOM, a mandatory global store, SSR/hydration, a CSS framework, AI, or a React/Vue compatibility layer. Advanced server work remains optional planned research.
