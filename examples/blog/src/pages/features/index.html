01 · begin

Start with one normal Vite entry point.

The recommended application bootstrap discovers pages, components, layouts, file API routes, and middleware conventions. Advanced apps can still use createViteApp() or createApp() explicitly.

src/main.jsJavaScript or TypeScript
import { mountVeloDom } from "velodom/vite";

await mountVeloDom();
Mental model: Folder = feature. HTML = template. A nearby script owns behavior, a config owns route policy and SEO, and the compiler assembles the resource map.

02 · authoring

Pages stay visible and close to their policy.

Folder mode is the default for a growing feature. The optional .vd format co-locates template, script, style, and config without replacing folders. Both use the same compiler and runtime contracts.

folder moderoute feature
src/pages/about/
├── index.html   # template
├── script.js    # state + lifecycle
├── style.css    # scoped presentation
├── data.js      # optional page data
└── config.js    # path, layout, guards, SEO

Shallow state is the shortest path to interaction.

Export plain defaults for simple behavior. Move multi-step work, async logic, event subscriptions, and cleanup into init().

src/pages/counter/state + event
<!-- index.html -->
<h1>{{ title }}</h1>
<button vd-on:click="count++">Count: {{ count }}</button>

// script.js
export const state = {
  title: "Hello VeloDom",
  count: 0
};

03 · templates

Directives add behavior without replacing HTML.

Preferred vd-* syntax is compiled and source-checked. Text interpolation is ideal for inline text; use vd-text when an element owns the whole value. Legacy data-vd-* input remains compatible for older templates.

conditions and loopssafe expressions
<p vd-if="Boolean(user)">Welcome {{ user.name }}</p>
<p vd-else>Please sign in.</p>

<ul>
  <li vd-for="post in posts" vd-key="post.id">
    {{ post.title }}
  </li>
</ul>
binding and form modeldeclarative UI
<input vd-model="draft.title" aria-label="Title">
<a vd-bind:href="post.url" vd-nav>Read post</a>
<div vd-class="{ active: isActive }"></div>
<div vd-style="{ color: accent }"></div>
Expression boundary: VeloDom parses expressions into an AST instead of using eval or new Function. Keep complex business logic in the page or component script.

04 · composition

Components and layouts are application-owned HTML.

Components are discovered from src/components. Use props for input, slots for markup composition, refs for deliberate parent-to-child commands, and expose for the child API. Layouts let groups of pages share navigation and footer shells without adding them to Core.

component useprops + slots + ref
<vd-component
  name="blog/post-card"
  vd-props="{ post: featuredPost }"
  vd-ref="featuredCard"
>
  <vd-child name="footer">Saved by the editor</vd-child>
</vd-component>

// parent script.js
state.openFeatured = () => {
  state.components.featuredCard?.open?.();
};
src/layouts/default.vdshared shell
<template>
  <vd-component name="nav"></vd-component>
  <vd-page></vd-page>
  <vd-component name="footer"></vd-component>
</template>

05 · navigation

Folder paths become predictable client routes.

Nested folders map to nested routes and bracket folders map to params. VeloDom also supports route config overrides, guards, query values, route metadata, focus management, scroll restoration, hashes, and opt-in link prefetch.

routing by conventionfolders first
src/pages/
├── index.html                 → /
├── blog/index.html            → /blog
└── blog/posts/[id]/index.html → /blog/posts/:id

<a href="/blog/posts/html-first" vd-nav>Read article</a>
<a href="/#requests" vd-nav>Jump to requests</a>
Same-page hashes: when only the hash changes, the router scrolls to the target directly instead of reloading the page.

06 · data and forms

Keep common request UX declarative; keep business rules in src/api.

File route discovery and explicit registries both produce named request handlers. The browser can bind a request to a result destination and derive loading/error state. Middleware, auth providers, retry, cache, debounce, throttle, hooks, and validation remain opt-in.

declarative requestautomatic state
<button
  vd-request="articles.getOne"
  vd-request-config="{
    params: { id: 'html-first' },
    target: 'articleResult',
    autoState: true,
    retry: 1
  }"
>
  Load article
</button>

<p vd-show="articleLoading">Loading…</p>
<p vd-if="articleError !== ''">{{ articleError }}</p>
<h3>{{ articleResult?.title }}</h3>
Try it: local request routevd-request

Progressive forms keep native HTML as the baseline.

native form + opt-in enhancementserver owns policy
<form action="/contact" method="post" vd-progressive-form vd-validate>
  <label>
    Email
    <input name="email" type="email" required>
  </label>
  <button type="submit">Send</button>
</form>

The server still owns authentication, CSRF, validation, redirects, and authorization. VeloDom only provides an optional HTML enhancement bridge.

07 · production

Move SEO, content, localization, and asset intelligence to build time.

Page config owns SEO metadata. Static route HTML, prerender entries, JSON-LD, sitemap and robots records are build output. Content, localization, and image helpers live in explicit Node/build subpaths so ordinary browser pages do not pay for them.

config.jsroute policy + SEO
export default {
  path: "/articles/:slug",
  seo: {
    title: "VeloDom articles",
    description: "HTML-first framework lessons.",
    canonical: "/articles",
    keywords: ["VeloDom", "HTML-first"],
    jsonLd: { "@type": "WebSite", name: "VeloDom" }
  },
  prerender: {
    entries: async () => [
      { path: "/articles/html-first", data: { title: "HTML-first" } }
    ]
  }
};
build-time localizationpublic subpath
import { createLocaleFormatter } from "velodom/localization";

const i18n = createLocaleFormatter({
  locale: "ar",
  messages: { welcome: "مرحبًا {name}" }
});

i18n.formatMessage("welcome", { name: "Nadia" });
content collectionbuild only
import { loadContentCollection } from "velodom/content";

const posts = await loadContentCollection({
  root: "src/content",
  collection: "posts",
  basePath: "/blog"
});
Terminology matters: static SEO HTML and prerender output are not request-time SSR. Client takeover is not hydration. velodom/node adapts Node HTTP to Fetch-style application handlers; it does not render templates or manage sessions automatically.

08 · developer experience

Project intelligence is development tooling, not browser weight.

The vd CLI reads the visible project structure and compiler metadata. It can diagnose, describe, graph, and measure an application without adding a telemetry service or a runtime panel to every page.

terminallocal project intelligence
vd inspect              # pages, components, APIs, refs, state
vd doctor               # broken refs, invalid config, maintainability hints
vd graph --mermaid      # static project relationships
vd health               # advisory quality score
vd build-report         # chunk and optimization signals
vd docs                 # generated project reference
vd types                # application-owned declarations
vd create page guide --demo seo

Testing

Use velodom/testing to mount public page/component resources in a browser-like test environment. Real-browser Playwright checks cover routing, forms, requests, and no-JavaScript SEO.

Editor intelligence

The compiler exposes diagnostics and directive completions for HTML and .vd documents. The optional VS Code tooling remains outside the application package.

09 · architecture

A small runtime is an architectural decision.

VeloDom Core receives resources from adapters. It does not discover your disk, own your business data, or import a framework-specific server. This boundary keeps an application free to use JavaScript or TypeScript while framework complexity stays inside a documented TypeScript package.

public importsstable boundaries
import { createApp, definePlugin } from "velodom";
import { mountVeloDom } from "velodom/vite";
import { compileTemplate } from "velodom/compiler";
import { mountTestPage } from "velodom/testing";

// Do not import velodom/lib/* or packages/velodom/src/*
// Those are framework internals, not application APIs.
Explicit non-goals: VeloDom does not require JSX/TSX, a virtual DOM, a mandatory global store, SSR/hydration, a CSS framework, AI, or a React/Vue compatibility layer. Advanced server work remains optional planned research.
